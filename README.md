# 选品销量监控 · 单机版

每小时把商品的累计销量抄一次，存进本地数据库，用相邻快照相减得到增量，算出**今日销量、爆品值、商品价值**，按四象限排出优先级。

配公众号「阿亮的修身炉」《把选品做成一套监控工具》那篇文章：文章讲为什么，这里讲怎么跑。

## 任务

解决一个具体问题：**累计销量看不出这个品现在还卖不卖。**

一个链接显示累计卖了一万单，可能是两年慢慢攒的（现在一天几单），也可能是两周前刚起量的（现在一天两百单）。数字一模一样，机会天差地别。

本工具把「累计销量」这个静止的数字，变成一条**随时间变化的速度曲线**，再用两个公式把候选池从一千个缩到十个。

**它只负责市场证据这一层。**

## 任务边界（先看这个）

选品是三种证据的交叉，本工具只做第一种：

| 证据 | 本工具 |
|---|---|
| 市场证据：有人买，而且**最近还在买** | ✅ 负责 |
| 内容证据：有人发，而且笔记能持续拿到流量 | ❌ 不负责 |
| 能力证据：我能做出合格产品并稳定生产内容 | ❌ 不负责 |

三个同时满足才值得真正投入。只有市场销量没有内容入口，商品可能不适合这个平台；只有笔记流量没有成交，可能只是大家爱看却不愿意买；只有你自己擅长没有市场验证，可能做出一份没人需要的东西。

**明确不做的四件事：**

1. **不预测。** 不预测这个品能卖多少、能赚多少钱。它只记录**已经发生**的变化。
2. **不替你做决策。** 它把范围从一千个缩到十个，最后那一步是人的判断。
3. **不判断你能不能做出来。** 一份需要大量录制的资料，成本可能远超收益——这条不成立，数据再漂亮也没用。
4. **不判断季节性。** 开学季资料、考试资料、节日模板都有明确时间窗口，等你做完产品窗口已经过去了。工具看不出来，只有你知道。

## 适合谁 / 不适合谁

**适合：**

- 做虚拟资料、知识付费，靠「跟品」起量的中小卖家
- 手上已经有一批候选商品，不知道哪个**正在起势**
- 愿意每天花五分钟看数据、每周淘汰一批换一批

**不适合：**

- 想找「一键爆款」的——这里没有预测，只有记录
- 想把几百个商品全塞进去的——维护不住，也会让你陷入"看了很多数据却没做任何产品"的假忙碌
- 指望它替你下结论的——它只负责缩小范围
- 电脑经常关机、没有稳定运行环境的——**快照必须连续**，断得多了数据就废了

## 使用前必读

使用本工具需要满足的前提，以及必须知道的风险：

**1. 它需要一台能持续运行的机器。**

快照必须连续。断一次就少一段，断在关键位置（当天第一条或最后一条）这一天的数就废了。可以是长期开机的电脑、NAS、或云主机。

**2. 一小时采集一次就够了。**

再密没有意义，只会增加被限制的风险。

**3. 登录态等于账号密码，别提交、别外传。**

`storage_state.json` 是你的小红书登录态。已在 `.gitignore` 排除，**别手动 add 它**，也别贴进任何对话。

**4. 只读取商品页公开可见的信息**，不绕过任何登录或付费墙。请遵守平台的使用条款。

**5. 平台一改版，选择器就可能失效。**

页面 DOM 会变，`fetch_live()` 里的选择器是兜底写法。发现大面积采不到时，先怀疑选择器，不是先怀疑代码逻辑。

**6. 数据只存在你自己的电脑上**，不上传任何地方。

## 30 秒先看效果

**只要 Python 3.7 以上**，不用装任何第三方库。命令里 `python` 跑不通的话，Windows 试试 `py`，macOS 试试 `python3`。

不用登录、不用配置，先把仓库拿下来，灌一段历史数据把逻辑跑通：

```bash
git clone https://github.com/aliang-ds/xhs-monitor.git    # 不想用 git，就点仓库页的 Code → Download ZIP
cd xhs-monitor

python monitor.py init --dir ./data
python monitor.py backfill 8 --dir ./data    # 灌最近 8 天的模拟数据
python monitor.py report --dir ./data        # 生成看板
```

> `backfill` 只对**自带的 12 个示例商品**有效。你一旦换成自己的清单，它就跑不出数据了 —— 那时改用 `fetch` 采真实数据。
> 每条命令都带 `--dir` 有点烦，可以先设一次环境变量省掉它，见下面「数据目录」。

打开 `data/out/report.html`，终端里是这样（**示例商品 + 模拟数据**的输出，你跑出来的应该跟它逐位一致）：

```

短视频脚本库          305    3130     10.3    1159.1   ①    强
AI提示词合集          174    3607     20.7     411.3   ①    中
冷启动起号日记          34     633     18.6     160.7   ①    中
小红书运营SOP手册      119    1605     13.5      87.3   ②    中
...
```

核心逻辑**零第三方依赖**，只用 Python 标准库。接真实数据时才需要 `playwright`（见下）。

## 命令速查

| 命令 | 作用 |
|---|---|
| `init` | 建库 + 在数据目录生成示例清单（12 个示例商品） |
| `add --url <链接> --title <标题> --price <客单价> [--shop <店铺>]` | 加商品进监控池 |
| `list` | 列出监控池 |
| `fetch` | 采集一次（真实模式，需登录态） |
| `fetch --mock` | 采集一次（模拟模式） |
| `backfill <天数> [--start <日期>]` | 灌模拟历史，**只对自带的示例商品有效**，用来先跑通逻辑 |
| `report [--day YYYY-MM-DD] [--split p75\|median\|value:200]` | 出看板 + 日报。不写 `--day` 就自动用**最近有数据的那天** |
| `verify` | 自检 |

### 数据目录

每个命令都能用 `--dir` 指定数据放哪。嫌每条都敲麻烦，就先设一次环境变量：

```bash
export XHS_DATA_DIR=./data          # macOS / Linux
set XHS_DATA_DIR=./data             # Windows cmd
$env:XHS_DATA_DIR="./data"          # Windows PowerShell
```

设好之后，所有命令都能把 `--dir` 省掉。

**建议把数据目录和脚本目录分开**，这样升级脚本不会把监控数据一起带走。

> 注意：如果你两条都不设，数据会落到 WorkBuddy 技能版的默认位置 `~/.workbuddy/xhs-monitor-data` —— 那是给技能专用的，普通用户不需要知道，所以**请务必显式指定一个目录**。

## 三个指标，口径要记牢

| 指标 | 公式 | 怎么读 |
|---|---|---|
| 今日销量 | 今日末条有效快照 − 今日首条有效快照 | 必须两条都在，缺首条就标「不完整」 |
| 爆品值 | 累计已售 ÷ 今日销量 | **越小越好**，越小说明这链接越新 |
| 商品价值 | 客单价 × 今日销量 ×（今日销量 ÷ 累计已售） | **越高越好**，同时奖励卖得多、链接新、客单价高 |

四象限：爆品值按固定阈值切（默认 `< 50` 算小），商品价值按分位切（默认 p75）。

```
              商品价值高              商品价值低
爆品值小   ① 最优先研究          ② 继续观察
爆品值大   ③ 学成熟模型          ④ 优先级最低
```

> ①是「最优先研究」，不是「直接复制」。进去之后还要拆竞品、看差评、问自己能不能做出差异。
> 四类不是永久身份：一个商品今天在①，七天后可能因为销量衰退掉进③。

> 商品价值是**重尾分布**，头尾常差三个数量级。
> 在自带的示例池（模拟数据）里：最大 1159，最小 0.8，中位数只有 7.0。
> 用中位数切会把日销十几单的小品也划进「高」区，所以默认用 p75，想换就 `--split median` 或 `--split value:200`。
> 换成你自己的池子后，建议重新核一次这几个数——分布变了，p75 未必还是最合适的分界。

## 三条铁律

破坏任何一条，数据就是假的。

**1. 采不到记 `NULL`，绝不记 0。**

0 是「卖了 0 单」，NULL 是「不知道卖了几单」。只要有一次失败记成 0，曲线就会从 2000 掉到 0，下次又从 0 涨回 2000——系统凭空造出两千单。**宁可显示一个横杠，也不要伪造一个 0。**

**2. 今日销量的基线必须是当天 0–1 点的那条。**

程序下午才开始跑的话，所谓「今日销量」只是下午以后的增量，跟完整自然日不能直接比。这一天会被标成「不完整」，不参与证据强度判定。同理，**新加进来的商品当天没有基线，明天起才算得准。**

**3. 一天 1 单也能算出漂亮的爆品值。**

累计从 1 变 2，爆品值就是 2。所以还要看**绝对销量**（日销 ≥ 20）和**连续性**（连续 3 天以上增长），两项都满足才算证据「强」。

小红书 web 端商品详情需要登录态 + `x-s` 签名，硬破解签名不划算——成本高、对方一改就得重写。这里的做法是**起一个真实浏览器**，登录态存在本地，从渲染后的 DOM 里读数字。

```bash
pip install playwright
playwright install chromium

# 用你自己的浏览器登录一次，把登录态存下来
playwright codegen --save-storage=<数据目录>/storage_state.json https://www.xiaohongshu.com

# 换成你要监控的商品
python monitor.py add --url "<商品链接>" --title "<标题>" --price <客单价>
python monitor.py fetch --dir ./data
python monitor.py report --dir ./data
```

短链（`xhslink.com`）取不出商品 ID，会明确报错——先用浏览器打开，复制跳转后的地址。

页面 DOM 会变，`fetch_live()` 里的选择器是兜底写法。第一次跑要核对一次：让浏览器打开页面截图，看数字在哪个元素里，把选择器改对。

## 常见误读

**「累计销量倒退」是 bug 吗？**

通常不是。它意味着这个链接**改过品**——历史评价和现在卖的东西对不上，就是因为改品了。也可能商品串了。真出现要人工去商品页看一眼，别直接改代码。

**①象限的商品可以直接跟吗？**

不能。①只说明「链接新、近期强、客单价或效率不错」，是研究的起点。往下还要问：我能不能做出可交付的产品、有没有优化空间、利润结构合不合理、是不是季节性波动。这四件事顺序不能跳——**你做不出可交付的产品，讨论优化空间就没有意义。**

**数据说它好，是不是就一定能做？**

不是。数据只能帮你缩小范围。真正的机会常藏在「已经有人买，但现有产品还不好用」的地方——看竞品的差评、评论区的追问、商品描述里没解决的问题。

## 自检

```bash
python monitor.py verify --dir ./data
```

检查三件事：失败有没有被记成 0、中间采不到时日销量还算不算得对、累计销量有没有倒退。

示例池（模拟数据）的自检结果：失败 7 条 / 被记成 0 的 0 条；某个商品在中间断掉 3 个小时的那天，日销 226，跟相邻两天的 216、266 吻合（说明 NULL 没污染计算）；累计销量倒退 0 次。

> 那 7 条失败是**示例数据故意注入的**——就是留给你跑 `verify` 验证用的。你换成真实数据后跑出来的数字会不一样，重点看三条结论的**方向**：失败数不为 0 但记成 0 的是 0、断采那天的日销跟相邻天持平、倒退次数接近 0。
